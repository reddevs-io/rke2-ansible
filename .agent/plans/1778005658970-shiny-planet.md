# Plan: Add RKE2 Worker Nodes to an Existing Cluster

## Goal

Introduce a new Ansible playbook `add_workers_rke2.yml` that joins one or more
fresh nodes as RKE2 agents (workers) into an already-running RKE2 cluster,
without touching any existing server or agent nodes.

The design mirrors the style and conventions of the existing `upgrade_rke2.yml`
playbook: role-based, sequential (serial) execution, health checks, and
idempotent where reasonable.

## User Decisions

- **Target hosts**: a new inventory group `rke2_new_agents` selects nodes to be
  joined. After a successful join, the operator moves them into `rke2_agents`.
- **Version**: match the RKE2 version currently running on the existing server
  nodes (auto-detected from the first reachable host in `rke2_servers`).
- **Join token**: must be supplied as an extra-var `rke2_token=...`.
  The playbook will fail fast if it is missing or empty.
- **Server URL**: must be supplied as an extra-var `rke2_server_url=...`
  (e.g. `https://k8s-vip.example.com:9345` or
  `https://192.168.178.198:9345`). The playbook fails fast if missing.
- **Labels / taints**: out of scope for this change; keep the config minimal
  (server URL + token only).

## Deliverables

1. New playbook: `add_workers_rke2.yml`
2. New role: `roles/rke2_agent_join/` (tasks + defaults)
3. Reuse existing role: `roles/rke2_prepare` (OS prep + conditional reboot)
4. Reuse existing role: `roles/rke2_install` (RKE2 binary install)
5. Update `inventory/example_hosts.yml` and `inventory/example_hosts.ini` with
   an example `rke2_new_agents` group (commented out by default).
6. Update `README.md` with a new "Adding Worker Nodes" section covering
   prerequisites, inventory, required extra-vars, usage, and troubleshooting.

No changes to `upgrade_rke2.yml` or any existing role behavior.

## Playbook Structure: `add_workers_rke2.yml`

Three plays:

### Play 1 — Preflight (`hosts: localhost`)

Purpose: fail fast on missing inputs before we touch any remote host.

- Assert `rke2_token` is defined and non-empty; fail with a clear message
  pointing at `-e rke2_token=...`.
- Assert `rke2_server_url` is defined, non-empty, and starts with `https://`;
  fail with a clear message pointing at `-e rke2_server_url=...`.
- Assert the inventory has at least one host in `groups['rke2_new_agents']`;
  fail with a message to populate the group or use `--limit`.
- Assert the inventory has at least one host in `groups['rke2_servers']`
  (needed for version detection); fail with a clear message otherwise.
- Optional: run `kubectl get nodes` and warn (not fail) if kubectl is not
  configured on the control node — post-join verification will be skipped
  gracefully.

### Play 2 — Detect target version (`hosts: rke2_servers[0]`)

Purpose: determine what RKE2 version to install on the new workers.

- Run on the first server host only (`run_once: true`, `any_errors_fatal: true`).
- Execute `/usr/local/bin/rke2 --version` (with fallback to
  `/var/lib/rancher/rke2/bin/rke2 --version`) and parse the version string
  (same parsing approach as `rke2_version_check`).
- Set a hostvar / group-level fact `rke2_target_version` on
  `groups['rke2_new_agents']` via `add_host` or `set_fact` +
  `delegate_facts: true`, so Play 3 can consume it.
- Fail if the version cannot be detected (empty string).

### Play 3 — Join new worker nodes (`hosts: rke2_new_agents`)

- `become: true`
- `serial: 1` — add workers one at a time so issues surface immediately.
- `any_errors_fatal: true` — stop on the first failure.
- Vars set on the play:
  - `rke2_type: agent`
  - `rke2_version: "{{ rke2_target_version }}"` (from Play 2)
  - Sensible defaults for `health_check_retries`, `health_check_interval`.

Tasks (in order):

1. **Prepare system** — `include_role: rke2_prepare`
   (apt update, dist-upgrade, conditional reboot). Same as the upgrade
   playbook.
2. **Write agent config** — `include_role: rke2_agent_join` (see below).
3. **Install RKE2 agent** — `include_role: rke2_install`
   - `rke2_skip_upgrade` is explicitly `false` here, so the install step runs.
   - The existing role already handles `rke2_type=agent`, restarts
     `rke2-agent.service`, and waits for it to be active.
4. **Enable rke2-agent service at boot** — `systemd: name=rke2-agent enabled=yes`
   (the install script typically does this, but we enforce it explicitly).
5. **Post-join verification** (`delegate_to: localhost`, `become: false`):
   - Wait for `kubectl get node {{ inventory_hostname }}` to return `Ready`
     (uses `health_check_retries` / `health_check_interval`).
   - Skip gracefully (with a debug message) if kubectl is not available on
     the control node.
6. **Display success message** for the joined node.

## New Role: `rke2_agent_join`

Minimal role responsible for writing the agent configuration **before**
`rke2_install` runs, so the very first start of `rke2-agent` joins the cluster.

### `roles/rke2_agent_join/defaults/main.yml`

```yaml
---
rke2_token: ""           # must be overridden via extra-var
rke2_server_url: ""      # must be overridden via extra-var
rke2_config_dir: /etc/rancher/rke2
rke2_config_file: /etc/rancher/rke2/config.yaml
```

### `roles/rke2_agent_join/tasks/main.yml`

1. Re-assert `rke2_token` and `rke2_server_url` are non-empty (defensive,
   in case the role is used outside the new playbook).
2. Ensure `/etc/rancher/rke2` exists (`file: state=directory`, mode `0755`).
3. Render `/etc/rancher/rke2/config.yaml` from a template with:
   ```yaml
   server: "{{ rke2_server_url }}"
   token: "{{ rke2_token }}"
   ```
   Mode `0600`, owner `root`. Use `ansible.builtin.copy` with `content:` (no
   Jinja template file needed — keeps the role self-contained and matches the
   minimal scope).
4. Notify / trigger is not needed: `rke2_install` will (re)start the service
   after this role completes.

No handler is required because the install flow always restarts the service.

## README Update

Add a new top-level section **"Adding Worker Nodes"** after the existing
"Upgrade Process" section, covering:

- Purpose and when to use it (vs. `upgrade_rke2.yml`).
- Prerequisites:
  - A healthy existing RKE2 cluster with at least one reachable `rke2_servers` host.
  - Join token obtained from any server node:
    `sudo cat /var/lib/rancher/rke2/server/node-token`
  - Server URL (typically `https://<server-or-vip>:9345`).
  - New worker nodes listed under `rke2_new_agents` in inventory.
- Required extra-vars: `rke2_token`, `rke2_server_url`.
- Example commands (INI + YAML inventory):
  ```bash
  ansible-playbook -i inventory/hosts.yml add_workers_rke2.yml \
    -e "rke2_server_url=https://192.168.1.10:9345" \
    -e "rke2_token=K10abc...::server:xyz..."
  ```
- Post-join step: move joined hosts from `rke2_new_agents` into `rke2_agents`.
- Troubleshooting:
  - Token mismatch / "failed to validate token".
  - Firewall: ensure TCP 9345 (supervisor) and 6443 (kube-api) are reachable
    from the new worker to the servers.
  - Version skew: verify detected target version in play output.
  - Node stuck `NotReady`: check `journalctl -u rke2-agent -f` on the worker.
- Update the "Files" tree to include the new playbook and role.

## Out of Scope

- Adding new **server** (control-plane) nodes — different flow; can be a
  follow-up.
- Node labels, taints, or extra agent config options.
- Removing / decommissioning worker nodes.
- Automatic token retrieval from a server (explicitly user-required extra-var).
- Automatic server URL discovery (explicitly user-required extra-var).

## Validation Strategy (manual, post-implementation)

1. Lint: `ansible-playbook add_workers_rke2.yml --syntax-check -i inventory/example_hosts.yml`.
2. Dry run against a lab inventory:
   `ansible-playbook -i inventory/<env>/hosts.yml add_workers_rke2.yml --check -e rke2_token=... -e rke2_server_url=...`
3. Real run against a single new node (`--limit new-worker-01`), then
   verify with `kubectl get nodes` that the node is `Ready` and on the
   expected version.
4. Re-run the playbook against the same host and confirm it is a no-op for
   the already-configured worker (config file unchanged, service active,
   verification passes).

## Risk / Edge Cases

- **Idempotency on re-run**: if the node already has `rke2-agent` installed
  and running, the install script is safe to re-run; the config file write is
  idempotent when content matches; restart in `rke2_install` will briefly
  bounce the agent. Acceptable for a join playbook; documented as such.
- **Token or URL wrong**: `rke2-agent.service` will fail to become active;
  the existing `Wait for RKE2 agent service to be active` step in
  `rke2_install` will time out and fail the play on that host.
- **Version detection fails**: Play 2 fails fast with a clear error before
  any new worker is touched.
- **Control node lacks kubectl**: post-join verification is skipped with a
  warning; the systemd service activity check still provides a strong signal.
