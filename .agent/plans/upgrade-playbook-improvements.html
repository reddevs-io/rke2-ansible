Implementation Principles

  • One concern per commit. Each fix is its own commit so failures can be bisected and rolled back cleanly.
  • Preserve the existing role boundaries. No role merges or renames — they map cleanly to the documented pipeline.
  • Don't change default behavior without an opt-in. New guards (e.g. downgrade protection) ship as allow_* flags defaulting to the safer value, not as hard failures.
  • Every change gets a verification step. Most can be validated with --check against an existing cluster; P0 items get a real-cluster smoke test.
  • No new role dependencies. Solutions should not require pulling in additional Ansible collections.

Phase 0 — Critical Bugs

P0 · 4 fixes

Correctness issues that cause wrong or surprising behavior on every run. Each is a small, surgical change. Ship as four separate commits behind a single PR.

#17Fix unconditional reboot in rke2_prepare Bug

Problem. The reboot module has no when: guard, so every node reboots on every run regardless of whether packages changed. The task name ("Reboot system if required") implies conditional behavior that does not exist.

Affected file

roles/rke2_prepare/tasks/main.yml

Change

Insert a guard task before the reboot that checks the Debian/Ubuntu reboot-required marker, then gate the reboot on it. Extend the marker check to also detect kernel package upgrades explicitly (the marker file is authoritative for stock Ubuntu).

- name: Check if reboot is required
  stat:
    path: /var/run/reboot-required
  register: reboot_required_marker

- name: Reboot system if required
  reboot:
    msg: "Rebooting system after package upgrade"
    connect_timeout: "{{ reboot_connect_timeout }}"
    reboot_timeout: "{{ reboot_timeout }}"
    pre_reboot_delay: "{{ reboot_pre_delay }}"
    post_reboot_delay: "{{ reboot_post_delay }}"
    test_command: uptime
  register: reboot_result
  when: reboot_required_marker.stat.exists

Notes

  • For RHEL-family hosts the marker path differs (/usr/local/bin/needs-restarting exit code). Out of scope here — the role currently only uses apt, so Ubuntu assumption holds. Add a TODO comment.
  • The existing when: reboot_result.rebooted guard on the subsequent wait_for_connection task is correct and stays — it just now actually does something meaningful.

#4Wire up drain_ignore_daemonsets and drain_force defaults Bug

Problem. The role defines drain_ignore_daemonsets and drain_force in defaults/main.yml and the README documents them, but tasks/main.yml hardcodes --ignore-daemonsets --force. The variables have no effect.

Affected files

roles/rke2_node_drain/tasks/main.yml roles/rke2_node_drain/defaults/main.yml

- name: Drain node

  register: drain_result
  changed_when: true

Add to defaults/main.yml:

drain_delete_emptydir_data: true

Verification

Phase 1 — Robustness & Safety

P1 · 6 fixes

Behavior-preserving hardening that prevents silent failures in production. These are the changes that matter most for unattended upgrade runs.

#9Add preflight validation play Robustness

Problem. Unlike add_workers_rke2.yml, the upgrade playbook has no preflight. Common failure modes (kubectl unreachable, empty inventory groups, API rate-limit) only surface mid-run.

Affected files

upgrade_rke2.yml roles/rke2_preflight/tasks/main.yml (new) roles/rke2_preflight/defaults/main.yml (new)

Change

Add a new first play targeting localhost that runs gather_facts: false and validates:

  • kubectl get nodes succeeds on the control node (kubeconfig is valid and API is reachable).
  • The rke2_servers group is non-empty.
  • At least one server is currently Ready (cluster is healthy enough to begin).
  • If rke2_version == "", the GitHub API is reachable for latest-version detection (delegated, non-fatal — version check role already handles failure gracefully).

Skeleton:

- name: Preflight Checks
  hosts: localhost
  become: false
  gather_facts: false
  tasks:
    - name: Verify kubectl is reachable
      command: kubectl get nodes -o name
      register: preflight_nodes
      changed_when: false

    - name: Verify rke2_servers group is non-empty
      assert:
        that:
          - groups.rke2_servers | default([]) | length > 0
        fail_msg: "Inventory must define at least one host in rke2_servers"

    - name: Verify at least one server is Ready
      shell: kubectl get nodes -l node-role.kubernetes.io/control-plane -o jsonpath='{.items[*].status.conditions[?(@.type=="Ready")].status}'
      register: preflight_server_ready
      changed_when: false
      failed_when: "'True' not in preflight_server_ready.stdout"

Verification

  • Run with an empty rke2_servers group and confirm the playbook fails fast at preflight, not mid-upgrade.
  • Run with a broken KUBECONFIG and confirm failure message is actionable.

#3Add rescue block for cordon state on failure Robustness

Problem. If Wait for node to be Ready in rke2_node_restore exhausts its retries, the host fails and Uncordon never runs. The node stays cordoned with no guidance to the operator.

Affected file

roles/rke2_node_restore/tasks/main.yml

Change

Wrap the three kubectl operations in a block/rescue. The rescue does not auto-uncordon (a failed node should stay cordoned) but prints an explicit remediation banner and re-raises the failure.

- name: Restore node after upgrade
  block:
    - name: Wait for node to be Ready
      shell: >
        kubectl get nodes {{ inventory_hostname }} -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'
      delegate_to: localhost
      become: false
      register: node_ready
      until: node_ready.stdout == "True"
      retries: "{{ health_check_retries }}"
      delay: "{{ health_check_interval }}"
      changed_when: false

    - name: Wait for pods (see #6 for tightened check)
      ...

    - name: Uncordon node
      command: kubectl uncordon {{ inventory_hostname }}
      delegate_to: localhost
      become: false
      register: uncordon_result
      changed_when: "'uncordoned' in uncordon_result.stdout"

  rescue:
    - name: Report node still cordoned
      fail:
        msg: >
          Node {{ inventory_hostname }} failed to become Ready after upgrade.
          The node remains CORDONED — do not uncordon until you have verified
          the rke2-{{ rke2_type }} service is healthy (journalctl -u rke2-{{ rke2_type }}).
          Once verified, run: kubectl uncordon {{ inventory_hostname }}

Design note

Why not auto-uncordon? If the node genuinely failed to come up, uncordoning would cause the scheduler to place workloads onto a broken node. Leaving it cordoned is the safer default. The rescue block's job is to make the failure loud and actionable, not to silently reverse the cordon.

#6Tighten pod readiness check Robustness

Problem. The current check until: "'Failed' not in pod_phases.stdout" passes immediately while pods are still Pending or ContainerCreating. On a freshly upgraded node this is the common state — the check is effectively a no-op.

Affected file

roles/rke2_node_restore/tasks/main.yml

Change

Require every pod phase on the node to be either Running or Succeeded. Use a JSON-path count to avoid string-substring false positives.

- name: Wait for all pods to be running on the node
  shell: >
    kubectl get pods --field-selector spec.nodeName={{ inventory_hostname }}
    -o jsonpath='{.items[*].status.phase}'
  delegate_to: localhost
  become: false
  register: pod_phases
  until: >
    pod_phases.stdout | split(' ') | length
      == pod_phases.stdout | regex_findall('Running|Succeeded') | length
  retries: "{{ health_check_retries }}"
  delay: "{{ health_check_interval }}"
  changed_when: false
  when: not (rke2_skip_upgrade | default(false))

Handle the empty-pods edge case (a node with zero non-DaemonSet pods): an empty stdout means zero pods to wait for, which is acceptable.

#2Preflight check: inventory hostname must match Kubernetes node name Robustness

Problem. Every kubectl operation in rke2_node_drain and rke2_node_restore uses {{ inventory_hostname }} as the node name. If the inventory uses IP addresses or aliases instead of the OS hostname, kubectl silently targets a non-existent node.

Affected file

roles/rke2_preflight/tasks/main.yml (added in #9)

Change

Within the preflight play (added by #9), assert that each inventory hostname appears in the list of Kubernetes node names:

- name: Verify inventory hostnames match Kubernetes node names
  assert:
    that:
      - item in (preflight_nodes.stdout_lines | map('trim') | list)
    fail_msg: >
      Inventory host '{{ item }}' is not a Kubernetes node name.
      kubectl operations use inventory_hostname as the node name; ensure
      your inventory uses the OS hostname (which RKE2 registers as the node name).
  loop: "{{ groups.rke2_servers + groups.rke2_agents | default([]) }}"
  when: item in preflight_nodes.stdout_lines
Implementation note. The when guard prevents the loop from failing on hosts that are intentionally not in the cluster yet. Consider whether you want a hard fail (recommended) or a warning. Default to hard fail.

#12Add any_errors_fatal to server play Robustness

Problem. With serial: 1 and no any_errors_fatal, a failed host marks the batch failed but the next serial iteration still runs. Server 3 could begin upgrading while server 2 is broken and cordoned, leaving the cluster in a split-version state.

Affected file

upgrade_rke2.yml

Change

Set any_errors_fatal: true on the server play only. Leave the agent play as-is: losing a single agent mid-run is recoverable; losing a second server may compromise etcd quorum.

- name: Upgrade RKE2 Server Nodes hosts: rke2_servers become: true serial: 1
- name: Upgrade RKE2 Server Nodes hosts: rke2_servers become: true serial: 1 any_errors_fatal: true

#10Verify node versions in post-upgrade check Robustness

Problem. The Post-Upgrade Verification play only checks that all nodes are Ready. It does not verify that nodes actually report the target RKE2 version — a node could fail to upgrade silently and still pass.

Affected file

upgrade_rke2.yml

Change

Add a version assertion task to the post-upgrade play. The target version fact is computed per-host during the run; surface it via a hostvars lookup.

- name: Collect running kubelet versions
  shell: kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"="}{.status.nodeInfo.kubeletVersion}{"\n"}{end}'
  register: node_versions_raw
  changed_when: false

- name: Display node versions
  debug:
    var: node_versions_raw.stdout_lines

- name: Verify all nodes report the target version
  assert:
    that:
      - target_version in node_versions_raw.stdout
    fail_msg: >
      Not all nodes report the target version {{ target_version }}.
      Node versions:
      {{ node_versions_raw.stdout_lines }}
  vars:
    target_version: "{{ hostvars[groups.rke2_servers[0]].rke2_target_version | default('') }}"
Caveat. kubeletVersion reports the Kubernetes version (v1.28.4), not the full RKE2 build tag (v1.28.4+rke2r1). The assertion should match on the prefix, not full equality. Use regex_search or normalize both sides before comparing.

Phase 2 — Hygiene & Dependencies

P2 · 3 fixes

Cleanup and dependency reduction. Lower production risk but improves maintainability and removes external runtime requirements.

#11Replace curl | jq with uri module Quality

Problem. rke2_version_check uses curl -s <github-api> | jq -r '.tag_name' delegated to localhost. This forces a jq dependency on the control node and is subject to GitHub's unauthenticated rate limit (60 req/hr per IP). The README incorrectly lists jq under "Target Node Requirements" — it's actually a control-node requirement.

Affected files

roles/rke2_version_check/tasks/main.yml roles/rke2_version_check/defaults/main.yml README.md

Change

Replace the shell pipe with the Ansible uri module, which parses JSON natively:

- name: Query latest available RKE2 version
  uri:
    url: "{{ rke2_github_api_url }}"
    method: GET
    return_content: true
    status_code: 200
    timeout: 15
  register: rke2_latest_response
  delegate_to: localhost
  become: false
  when: rke2_version == ""

- name: Set latest version fact
  set_fact:
    rke2_latest_tag: "{{ rke2_latest_response.json.tag_name | default('') }}"
  when: rke2_version == ""

Update downstream logic to read from rke2_latest_response.json.tag_name instead of rke2_latest_version_raw.stdout. Add an optional github_token var in defaults that, when set, is sent as Authorization: token ... to raise the rate limit to 5000 req/hr.

Update README: move jq from "Target Node Requirements" to a removed note, or note that it is no longer required at all.

#8Add downgrade guard with opt-in flag Quality

Problem. Version comparison is plain string equality. If an operator passes an older rke2_version, the playbook proceeds with a downgrade without warning — risky and rarely intended.

Affected files

roles/rke2_version_check/tasks/main.yml roles/rke2_version_check/defaults/main.yml

Change

Add a new default allow_downgrade: false. After computing installed and target versions, compare them and fail unless downgrade is explicitly allowed.

# in defaults/main.yml
allow_downgrade: false

# in tasks/main.yml, after versions are known
- name: Detect attempted downgrade
  set_fact:
    rke2_downgrade_attempted: >
      {{ rke2_installed_version is version(rke2_target_version, 'gt') }}
  when:
    - not rke2_version_check_failed
    - not rke2_skip_upgrade | default(false)

- name: Refuse downgrade unless explicitly allowed
  fail:
    msg: >
      Installed version {{ rke2_installed_version }} is newer than target
      {{ rke2_target_version }}. Downgrade is dangerous and refused by default.
      To proceed, set: -e allow_downgrade=true
  when:
    - rke2_downgrade_attempted | default(false)
    - not allow_downgrade

Use Ansible's version comparison filter (not string comparison) so v1.28.10 > v1.28.4 is correctly evaluated.

#7Gate rke2_prepare heavy operations on skip flag Quality

Problem. rke2_prepare runs apt dist-upgrade and the (currently unconditional — see #17) reboot before rke2_version_check. A node already at the target version still gets a full OS upgrade and reboot, which is unnecessary downtime if the operator only wants the RKE2 step.

Affected files

upgrade_rke2.yml roles/rke2_prepare/tasks/main.yml roles/rke2_prepare/defaults/main.yml

Change

Two-part change:

  1. Reorder the tasks in upgrade_rke2.yml so rke2_version_check runs first, then rke2_prepare is included with a when: not rke2_skip_upgrade guard.
  2. Add a new default prepare_always_runs: false. When true, restores the old behavior for operators who want OS patching regardless of RKE2 skip.
- name: Prepare system include_role: name: rke2_prepare - name: Check RKE2 version include_role: name: rke2_version_check
- name: Check RKE2 version include_role: name: rke2_version_check - name: Prepare system include_role: name: rke2_prepare when: > (not (rke2_skip_upgrade | default(false))) or (prepare_always_runs | bool)
Trade-off to confirm with operator. Some teams want OS patching on every playbook run regardless of RKE2 state. The prepare_always_runs flag preserves that option. Default to false (skip on no-op runs) but surface this as an open question below.

#14Improve changed_when on drain task Quality

Problem. changed_when: true on Drain node always reports changed, even when no pods were evicted. Cosmetic but noisy in CI/CD reports.

Affected file

roles/rke2_node_drain/tasks/main.yml

Change

Mark changed only when the drain output indicates eviction occurred:

  changed_when: >

Explicitly Out of Scope

  • RHEL/CentOS support. The rke2_prepare role uses apt exclusively. Adding dnf/yum branches and a RHEL-specific reboot-required detection is a separate effort.
  • Merging the server and agent plays. Considered and rejected — the two-play structure is what enforces servers-before-agents ordering without depending on inventory sequence. Keep as-is.
  • Replacing rke2 --version parsing with systemctl show. The awk '{print $3}' approach was reviewed and found stable. Not worth the churn.
  • Molecule test scaffolding. Would add real value but is a separate workstream. Recommend a follow-up plan after Phase 1 lands.
  • Auto-rollback on failure. Too risky to automate. Operators should roll back by re-running with a pinned older rke2_version, as documented.

Open Questions for Operator

These need a decision before the relevant commit lands:

  1. #5 — remove or wire up service_start_timeout? Plan defaults to remove. If you want it to bound the absolute wait time on the service-check task, say so and it becomes a real timeout wrapper.
  2. #7 — should OS patching run on no-op upgrades? Plan defaults to skip when rke2_skip_upgrade via prepare_always_runs: false. If your team relies on the playbook also keeping nodes patched regardless of RKE2 state, set the default to true.
  3. #2 — hard fail or warn on inventory/hostname mismatch? Plan defaults to hard fail. A warning-only mode is reasonable if you have legacy inventories being migrated.
  4. #12 — extend any_errors_fatal to agents too? Plan applies it to servers only (etcd quorum risk). If you want the agent play to also halt on first failure, the change is one line.
  5. Verification environment. Phases 0 and 1 really need a live multi-node cluster to validate (cordon behavior, reboot gating, rescue flow). Is there a staging cluster available, or should we invest in a local multi-node vagrant/libvirt setup first?
